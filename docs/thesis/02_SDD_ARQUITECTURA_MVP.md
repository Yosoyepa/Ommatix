# 02. Software Design Document: arquitectura del MVP

## 2.1 Propósito, estado y alcance

Se conserva la dirección de la conversación: un runtime Rust local, un estado espacial en RAM y una interfaz MCP que permite planificar sin generar coordenadas [F0, pp. 22–24]. Esta revisión especifica **un MVP funcional de control visual**; no confunde el prototipo de algoritmos entregado con el producto terminado.

**Supuesto aprobado el 14 de octubre de 2026 ([ADR-0008](../adr/0008-one-real-platform-first.md)):** primera plataforma Windows 11 x64, escritorio interactivo local, un monitor seleccionado, SDR/BGRA y aplicaciones de prueba sin privilegios elevados. Resolución base 1920×1080; escalas de validación 100%, 125% y 150%. Interfaces en español e inglés, lectura horizontal LTR. Las aplicaciones de prueba siguen pendientes de aprobación. Otras plataformas se mantienen como puertos futuros, no como capacidad implícita.

El alcance mínimo incluye captura real, detección/OCR reales, los tres bloques core, identidad persistente, observación MCP, click/type/scroll bajo política y verificación posterior. Se excluyen entrenamiento desde cero, control de UAC/escritorio seguro, ejecución remota por red, soporte universal de aplicaciones, drag-and-drop y macros especulativas. La clasificación semántica abierta de iconos no es obligatoria: el estado desconocido es válido.

## 2.2 Contexto y límites de confianza

El usuario autoriza un host/agente a usar una instancia del motor. El agente entrega intenciones por MCP y recibe datos estructurados potencialmente sensibles. El sistema operativo y las aplicaciones cambian de forma asíncrona; su contenido visual se trata como **datos no confiables**, no como instrucciones de política. Un texto OCR que ordene “ignora tus reglas” no cambia permisos.

La instancia está vinculada a una sesión de usuario y a un monitor/ventana permitido. La política local, fuera del control del agente, decide qué aplicaciones y acciones están habilitadas. No se abre un puerto TCP en el MVP. El transporte stdio no elimina riesgos de un cliente local malicioso; se restringen su lanzamiento y el acceso a las credenciales del usuario.

## 2.3 Estructura de componentes

| Componente | Responsabilidad | Contrato principal |
|---|---|---|
| MCP Adapter | Validar y enrutar llamadas; describir herramientas | Tool inputs/outputs versionados |
| Observation Coordinator | Captura, planificación de regiones y commit | SnapshotRequest → Snapshot |
| Capture Provider | Pixels, stride, tiempos, dirty/move rects | FrameLease |
| Perception Provider | Detector, OCR y transformaciones de imagen | Region → RawEvidence |
| Accessibility Provider | Árbol de accesibilidad de la ventana en primer plano (UI Automation); evidencia opcional que se fusiona con la visual | Region → AccessibleElement |
| Spatial Fusion | Contención, renglones, etiquetas y relaciones; absorbe las detecciones que coinciden con un elemento accesible | RawEvidence + AccessibleElement → Candidates |
| Icon Resolver | Recuperación contextual con rechazo | CropDescriptor → LabelEvidence |
| Temporal Registry | IDs, revisiones y bajas | Candidates + Snapshot → Tracks |
| Policy & Action Gate | Vigencia, permisos y precondiciones | ActionRequest → Permit/Reject |
| OS Actuator | Inyección de eventos y conteo de entrega | ValidatedAction → DeliveryReceipt |
| Effect Verifier | Comprobar un efecto esperado o incertidumbre | Before/After → Verification |
| Telemetry | Métricas y auditoría sin texto sensible | Events/Spans |

Se propone un **monolito modular**, no una colección de microservicios. Los frames se pasan como leases/buffers con propietario explícito; los índices y tablas se mantienen en memoria. No se necesita Redis para unos cientos de elementos. Separar captura/inferencia en procesos sólo se reconsiderará si aislamiento o perfiles reales lo justifican.

## 2.4 Puertos y adaptadores

La lógica core no depende directamente de DXGI, ONNX ni MCP. Los puertos `FrameCapturer`, `VisionDetector`, `TextRecognizer`, `AccessibilityProvider`, `OsActuator`, `Clock` y `PolicyStore` permiten sustituir adaptadores por fixtures deterministas. Los resultados deben incluir procedencia, frame/region de origen y calidad de evidencia. Para ADR-0032, `OsActuator` puede atestiguar una lista completa y ordenada por z-order/handle de ventanas visibles con rectángulos físicos opcionales en `TopLevelWindow`; el valor por defecto del puerto es `None`, que exige la pantalla entera. Las consultas existentes de primer plano y del punto pueden omitir el rectángulo: sólo la lista completa lo acredita, sin añadir lecturas DWM al alcance `screen`.

**Windows:** DXGI es el candidato de captura; primero se aprovechan move/dirty rects nativos y después el diferenciador propio como respaldo o verificación [S06]. El actuador candidato es SendInput, con recuento de eventos y restricciones documentadas [S07]. Las llamadas se hacen en el contexto de usuario, sin técnicas para evadir controles de seguridad.

**Accesibilidad (ADR-0017):** `AccessibilityProvider` entrega los elementos de la ventana en primer plano atestiguada, dentro de las regiones planificadas (toda la ventana en un refresco completo): caja en píxeles físicos del monitor seleccionado y recortada, rol derivado del tipo de control de UI Automation (`Button`/`SplitButton` → `button`; `Edit` escribible y no contraseña → `input`; `CheckBox` → `checkbox`; `ComboBox` → `dropdown`; el resto de controles accionables → `unknown`; los demás tipos se omiten), nombre, `enabled`, `offscreen`, `password` y los patrones de acción que admite (`Invoke`, `Toggle`, `Value`, `ExpandCollapse`, `SelectionItem`, `Scroll`). Es evidencia positiva que se **fusiona** con la visual, no la sustituye: un elemento habilitado, en pantalla y con un patrón de acción es `confirmed`; las detecciones visuales que son el mismo control (IoU o IoC, Algoritmo 2) se absorben en él y su rol y su nombre ganan (`label_source: accessibility`); las demás detecciones quedan como están, salvo que pierden una accionabilidad confirmada si su centro cae sobre un elemento accesible. Nunca se lee `ValuePattern.Value`, un campo de contraseña nunca es `input` ni publica texto, y los nombres son datos no fiables. Está apagado por defecto (`NoAccessibility`); su etapa se mide aparte (`accessibility` en `_meta`). **Lectura acotada:** el recorrido tiene un presupuesto (elementos, profundidad y tiempo). Si termina por él, el proveedor lo declara (`truncated`): lo que falta es desconocido, no ausente. Las regiones leídas quedan como huecos y la siguiente observación vuelve a leerlas aunque ningún píxel haya cambiado; mientras un hueco exista, la evidencia que la lectura parcial no repite se conserva si los píxeles no cambiaron, y una detección visual sin elemento accesible dentro del hueco no queda `confirmed`. `observe_screen` informa en `_meta` si la evidencia es completa (`io.ommatix/accessibility`).

**Inferencia:** ONNX Runtime detrás de un puerto; CPU es baseline, DirectML una opción inicial de Windows y WinML una evolución evaluable. DirectML tiene restricciones de concurrencia por sesión y de configuración que el adaptador debe respetar [S09–S10]. Los modelos/pesos se eligen en el spike S0; ninguna tabla de roles se inventa a partir del nombre “YOLO”. Un detector binario interactuable/no-interactuable no se convierte automáticamente en detector de inputs, dropdowns y checkboxes.

**MCP:** preferencia por SDK `rmcp`, fijando versión compatible con el perfil acordado [S23]. El protocolo 2026-07-28 y el legacy 2025-11-25 tienen reglas distintas; se documentan en el contrato de transporte. No se implementa JSON-RPC casero como sustituto de toda la conformidad MCP.

## 2.5 Modelo de datos interno

**Frame:** dimensiones físicas, stride en bytes, formato BGRA8, instante monotónico de captura, identidad de monitor, rotación, epoch geométrico y procedencia de regiones de cambio. La longitud y los productos de dimensiones se validan con aritmética comprobada. No se asume que `row_stride == width*4`.

**RawEvidence:** bbox/polígono, tipo de evidencia, texto opcional, score del proveedor, transformación del tensor al recorte, detector/modelo/revisión y `source_frame_id`. Los scores se conservan por separado para no multiplicarlos como probabilidades independientes sin calibración.

**Element:** `target_id` opaco, revisión monotónica, rol o `unknown`, etiqueta con procedencia, contenido interno con `text_kind`, bbox física, soporte de evidencia, grupo/ventana, visibilidad, habilitación y `actionability`. La geometría permanece interna; se puede exportar sólo en diagnóstico local explícito.

**Snapshot:** `session_id`, `snapshot_id`, `geometry_epoch`, `captured_at`, `published_at`, elementos, relaciones, estado de degradación y métricas. Las listas tienen orden estable por ID o por clave de lectura; no dependen del orden arbitrario de un HashMap.

## 2.6 Identidad y consistencia temporal

Los IDs se asignan al nacer un track, no se recalculan desde su posición. Un contador creciente de sesión evita colisiones por hash y no se reinicia al insertar un popup. La sesión forma parte del alcance de la referencia. La revisión aumenta si cambia un dato que afecta una acción: geometría, contenido discriminante, visibilidad, habilitación o contexto.

Se realizan asociaciones uno-a-uno con gates de contexto y opción de no asignación. Ante filas duplicadas, virtualización, desaparecidos o baja evidencia, se crea un track nuevo o se marca ambiguo. No se reancla silenciosamente una acción. Los tombstones impiden reutilizar IDs retirados durante la misma sesión.

**Política MVP estricta:** una acción debe referenciar el último snapshot publicado, la revisión del target y el epoch vigentes. Un popup no cambia la identidad del resto de tracks, pero puede volver obsoleta una observación para actuar. Se pide una nueva observación. ADR-0032 diseña esa validación opcional por grupo de ventanas, apagada por defecto; sus pruebas sintéticas no sustituyen M1 ni IT-08. La vigencia temporal (ADR-0025) es un límite más de la misma observación: la captura del snapshot caduca a los `max_snapshot_age_ms` (10 000 ms por defecto) y la lectura de accesibilidad que confirma un objetivo, a los mismos ms desde que empezó la lectura; una publicación nueva no renueva una lectura antigua, y la siguiente observación relee las regiones cuya evidencia ha caducado. Se comprueba en la puerta, también en simulación, y justo antes de cada entrada real.

## 2.7 Concurrencia y publicación transaccional

Un coordinador es el único escritor del estado publicado. Captura, detector y OCR pueden trabajar de forma concurrente, pero sus resultados están etiquetados con el frame y la configuración. Se proponen colas acotadas y política latest-wins para capturas aún no procesadas; una acción nunca se descarta sin respuesta explícita.

El procesamiento regional se construye en un estado candidato. Sólo al terminar validaciones se publica de forma atómica un snapshot inmutable, incluyendo registro e índice coherentes. Si una región falla, se preserva el estado anterior para inspección y se marca degradación; se bloquea actuar sobre evidencia obsoleta. No se adelanta el framebuffer base confirmado mientras haya trabajo sucio pendiente.

Un cambio de monitor, DPI, rotación, ventana fuera de política o configuración de modelos incrementa el epoch y dispara reconstrucción completa. Resultados de inferencias con epochs viejos se descartan sin publicarse. La cancelación impide nuevas etapas; si una entrada ya se entregó, el resultado debe reflejarlo y no fingir rollback.

## 2.8 Coordenadas y transformaciones

El core usa píxeles físicos del monitor seleccionado y cajas semiabiertas. Para cada inferencia se guarda la transformación completa: recorte, escala, padding, rotación y traslación a escritorio. Para letterboxing, `x_crop=(x_tensor-pad_x)/scale` y análogamente para Y; después se aplica el origen del recorte y, cuando corresponda, el del monitor. Los valores se recortan a límites válidos antes de elegir un punto.

El punto se selecciona dentro de una región visible válida y con margen a bordes. El centroide es un candidato, no una prueba de clic seguro. Elementos tapados, deshabilitados, degenerados o de accionabilidad desconocida no reciben permiso. El adaptador de Windows declara su política DPI y prueba las conversiones, incluida la normalización necesaria para la API de entrada [S08].

Aunque el MVP opere un monitor, las estructuras deben permitir orígenes de escritorio negativos. La compatibilidad multimonitor, HDR y rotaciones adicionales queda fuera de aceptación inicial hasta contar con casos reales.

## 2.9 Ejecución y verificación

Flujo: validar schema → deduplicar request_id → comprobar política → comprobar sesión/snapshot/revisión/epoch → confirmar ventana/foco, frescura y vigencia (ADR-0025) → preparar acción → registrar intención → inyectar eventos → comprobar entrega → observar efecto esperado → registrar resultado.

`type` requiere un control de entrada confirmado y foco verificado. No se escribe en un campo sólo porque exista texto cercano. Con evidencia de accesibilidad (ADR-0017, `[models] accessibility = "uia"`), el motor entrega `type` en dos fases y el foco se verifica sobre el elemento, no sobre la ventana (ADR-0018): (a) entrega el clic de enfoque en el objetivo, con las mismas comprobaciones de cualquier acción real (aplicación en primer plano atestiguada, parada y política); (b) consulta el elemento con foco de teclado, dentro del plazo de verificación y con el puerto `Clock`, y sólo lo da por confirmado si es el propio elemento objetivo, es decir, una entrada habilitada, en pantalla, que no es de contraseña y cuya caja coincide con la del objetivo por el mismo IoU con que la fusión decide que dos cajas son el mismo control; (c) sólo entonces entrega las teclas, tras una última mirada a la parada, el consentimiento y la aplicación en primer plano; (d) si el foco no se confirma a tiempo no envía ninguna tecla: el resultado es `indeterminate` (`INDETERMINATE_EFFECT`, `reconcile_effect`) con `input_delivered` verdadero, porque el clic sí se entregó, y no se reintenta ni se deshace. La consulta del foco es una lectura: no mueve el foco ni lee el valor del campo. Sin evidencia de accesibilidad, `type` conserva la comprobación de foco a nivel de ventana del actuador entre su clic y sus teclas, que no detecta que la aplicación aún no haya concedido el foco al campo. `scroll` declara dirección y magnitud limitada. `click` no obtiene confirmación implícita de efectos destructivos por ser un clic. El MVP sólo actúa dentro de aplicaciones y flujos controlados.

El bloqueo interno evita carreras del propio proceso, no congela el escritorio. Existe una ventana residual entre verificar e inyectar. Se reduce con revalidación inmediata y se documenta; no se promete imposibilidad física de clics equivocados en interfaces arbitrarias.

La verificación distingue: eventos entregados, cambio visual detectado y postcondición comprobada. Son evidencias diferentes. Un fallo de verificación produce `indeterminate`, no un reintento automático. En `type` en dos fases, la postcondición `visual_change` se mide contra un fotograma capturado después del clic de enfoque y antes de las teclas, nunca contra el fotograma previo al clic: el redibujado del propio clic no es el efecto de escribir. El efecto se busca dentro de un plazo acotado que fija el operador (`[engine] verify_timeout_ms`, 500 ms por defecto, como máximo 5000): tras entregar, el motor captura enseguida y, mientras no vea cambio respecto al frame previo a la entrega, espera `verify_poll_ms` (50 ms por defecto, de 1 a 1000) con el puerto `Clock` y vuelve a capturar, hasta que vence el plazo. Un cambio dentro del plazo es `effect_observed`; si vence sin él, `indeterminate`. Durante el plazo sólo se vuelve a leer la pantalla, nunca se reenvía la entrada, y no se publica ningún snapshot. Un plazo 0 es una única comprobación inmediata. Las corridas supervisadas de S3 mostraron que una sola captura justo después de entregar llega antes de que la aplicación redibuje. Para operaciones con efectos, un request_id repetido devuelve el resultado almacenado; una caída después de enviar entrada exige reconciliación, no suposición de exactly-once.


**Alcance de frescura opcional (ADR-0032).** `[engine] action_freshness = "screen"` conserva la pantalla entera por defecto. `"target_window"` compara exactamente los tiles que intersecan el grupo atestiguado por el SO: ventana bajo el punto del objetivo durante la observación, ventana de primer plano y ventanas de nivel superior cuyos rectángulos se solapan con alguna de esas dos semillas. No es un cierre transitivo ni una envolvente que incluya los huecos. Los rectángulos son píxeles físicos del monitor seleccionado, recortados; `action_freshness_margin_px` es un entero de 0 a 4294967295, cero por defecto, y extiende cada rectángulo antes de recortarlo. Aumentarlo sólo añade tiles comparados. La geometría y la época siempre se validan globalmente. La observación conserva la evidencia de ventanas junto al snapshot, tras lecturas iguales alrededor de la captura y una confirmación al ligar los objetivos a sus ventanas. Antes de la entrega se toman dos lecturas alrededor de la nueva captura; sin atestación completa, si difieren o si la caja objetivo no cabe en su ventana se usa la pantalla entera. La identidad del grupo (semillas, orden z, handle y rectángulo) se vuelve a leer después de la última mirada existente: un cambio rechaza con `STALE_SNAPSHOT` y gasta el snapshot incluso sin repintado. Tras ese recorrido se revalidan parada, consentimiento, aplicación, alcance por ventana y edad para que su duración no prorrogue una autorización. Si se pierde la atestación final, se exige la comparación global sobre el frame ya capturado. Un cambio conocido de la ventana observada sigue rechazando aunque la caja objetivo ya no quepa o falte la lectura del punto: el retorno a la comparación global no borra esa evidencia de identidad. La simulación termina antes de capturar y no predice el rechazo por píxeles. En `type` sólo cambia el chequeo anterior al clic de enfoque; las teclas siguen esperando foco sobre el propio elemento. El efecto visual se mide siempre sobre la pantalla entera. No se toleran píxeles distintos ni se enmascara el cursor de texto. D0 sólo expone recuentos en `_meta` (capítulo 07); M1 e IT-08/M2 siguen pendientes de ejecución supervisada.

**Grupo enmendado (ADR-0035, propuesto; implementado bajo el mismo valor `target_window`, apagado por defecto).** Con la implementación de la propuesta, el grupo de un objetivo `T` es la ventana de nivel superior que lo contiene más cada ventana visible **por encima** de `T` en el orden z cuyo rectángulo solapa el de `T` ampliado por `action_freshness_margin_px`. Las ventanas por debajo de `T` quedan fuera, y la ventana de primer plano sólo entra si cumple esa misma regla. El handle de la ventana de primer plano observada es un campo de identidad aparte: cualquier cambio de ese handle rechaza con `STALE_SNAPSHOT`, haya o no ámbito de ventana del operador. La identidad del grupo es la lista ordenada de sus miembros (rango dentro del grupo, handle, clase y rectángulo), de modo que el cierre de una ventana superior que no solapa no la cambia, pero un intercambio de orden entre miembros, una entrada, una salida o un cambio de rectángulo sí. El puerto `OsActuator::window_opacity` debe atestiguar que `T` es opaca (sin estilo en capas, transparente a clics ni sin bitmap de redirección, esto último porque DirectComposition puede componer con alfa por píxel sin capas; sin material de fondo del sistema distinto de `AUTO`/`NONE`; un estilo cero sólo vale si la consulta no dejó error, y una enumeración de ventanas con error no es completa) y la caja objetivo no puede tocar un cuadrado de 32 píxeles físicos en ninguna de las cuatro esquinas de `T`; lo que no se atestigua devuelve `None` y se compara la pantalla entera. El resto de ADR-0032 (geometría y época globales, comparación exacta sin tolerancia ni máscara, las dos lecturas del grupo alrededor de la captura, D0 sólo en `_meta`) no cambia.

## 2.10 Rendimiento y degradación

Se miden por separado captura, preparación, detección, OCR, fusión, tracking, serialización y verificación. El límite del core no incluye modelos; el de percepción sí. La inferencia del planificador y el tiempo de aplicación se miden fuera de esos segmentos. El selector regional compara número de inferencias y shapes contra el coste full-frame; área menor no implica cómputo menor.

Ante saturación se reduce frecuencia de observación, se agrupan regiones, se usa full-frame cuando convenga o se informa degradación. No se reduce seguridad para mantener FPS. La meta de actualizaciones pequeñas sub-10 ms se conserva como objetivo de optimización del núcleo, no como promesa del sistema completo.

## 2.11 Distribución y operación

El paquete productivo incluirá binario, librerías nativas necesarias, configuración, pesos autorizados o instrucciones de obtención, hashes y avisos. “Rust” no implica que ONNX y los modelos queden mágicamente embebidos en un ejecutable estático. Un chequeo inicial informa versión de runtime, proveedor, modelos disponibles y permisos; si falta un requisito, falla de forma explicativa y deja actuadores deshabilitados.

El proceso emite sólo mensajes de protocolo en stdout; diagnósticos van a stderr. Se limita el tamaño de solicitudes, resultados, textos, recortes y cachés. No hay retención de screenshots por defecto. Se soporta parada local independiente del agente.
