# 0033. Allow an external decision model only in an offline experiment on synthetic scenes

- **Status:** Proposed
- **Date:** 2026-10-17
- **Approval:** Pending. The project owner decides. Acceptance would change no test status and no checkbox of chapter 06 §6.7.

## Context

Ommatix perceives; the agent reasons (AGENTS.md §1). The thesis asks whether a structured
snapshot, with stable element identifiers, is enough for an agent to act by `target_id` and
revision instead of by coordinates. So far the only agents that read the contract are the
supervised test clients, which follow a fixed script. The question that has no evidence yet
is what a cheap, fast decision model does with the page: whether it names the right element,
whether it says "none" when no element can achieve the goal, how it reads a label that tries
to redirect it, and how much of its error the engine's gate would refuse anyway.

SubQ offers such a model as a hosted Decisions API (`POST /v1/systemone`, model
`subq-snap-preview`). It answers named questions over a state: a choice among 2–255 options,
a yes/no probability (`noul`) and a score; it bills input tokens only. A feasibility probe by the
architect (seven cases, about 4.3 thousand tokens) found that it grounds a goal to the right
target on the simulator's form and resists a label injection, but that it does **not** abstain on
impossible goals: it chose a button with confidence 0.91–0.95. A separate yes/no question
("is the goal achievable?") caught a case where only disabled elements matched (0.14) and missed a goal
about a dialog that is not on screen (0.97). The experiment has to measure exactly that.

Sending an observation to a third-party service is sending screen content to a third party.
ADR-0012 says that screen values do not leave the machine by default, and that text on screen
never changes permissions. The project must not weaken either rule to run an experiment.

## Decision

An external decision model may be used under these conditions, and only these:

1. **Only in an operator-side experiment tool.** The tool is `tools/agent/subq_decisions.py`. It is
   run by hand by the architect or the owner. It is not part of the `ommatix` binary, the library
   crates or any adapter; no crate depends on an HTTP client for it, and `serve` and `demo` never
   call it.
2. **Only on synthetic scenes generated by the repository, by the tool itself.** The tool does not
   accept a scenes file. It runs `cargo run --frozen --quiet -p ommatix-acceptance --example
   agent_scenes` (`--frozen` is locked and offline, so neither a run nor `--plan` reaches a network)
   from the checkout it lives in (resolved from its own path), into a fresh temporary directory
   outside the checkout, and reads only that output. `cargo` is resolved once to an absolute path
   and runs with a minimal environment (the tool keeps `PATH`, the system and user directories,
   `CARGO_HOME`, `RUSTUP_HOME` and the temporary directory, and drops every runner, wrapper, flag and
   target-directory override). The example
   (`src/acceptance/examples/agent_scenes.rs`) builds the real `Engine` over `SimulatedDesktop` and
   `FixtureDesktop`. A file that declares itself synthetic proves nothing, since a wrapper could carry
   live labels under the same markers, and running the generator is not proof either, since
   a runner, a `cargo` earlier on `PATH` or a planted build artefact can stand in for it. So the
   output is **pinned**: the scenes are deterministic, their SHA-256 is committed as a constant in
   the tool (`PINNED_SCENES_SHA256`) and in a test of the generator
   (`ag_01_the_scenes_match_the_pinned_hash`), and the tool builds no request unless the bytes it
   generated hash to that value, as every artefact the engine loads is pinned (ADR-0021). A change
   to the generator that does not update both places fails CI. The markers and the shape of the
   output are still checked as a sanity test, and a goal whose expected target is not in its scene
   is refused. **Threat model:** the pin prevents the tool from sending anything but the canonical
   synthetic scenes, whatever stands in for the generator; a compromised operator machine (one that
   can edit the tool or the pin, or read the key) is out of scope. `--scenes-out` only saves a copy of what was
   generated and is never read back. Tests replace the generator through a function parameter, never
   through a command-line option that takes a path or a program.
3. **Never on a live observation.** No frame, capture, accessibility tree or screen text of a real
   desktop is sent to the service, and the tool has no way to read one. The same holds for
   recorded sessions of the supervised rounds.
4. **Never in the product, never in CI with a network.** No code path of the engine depends on the
   model's answer. CI runs the tool's unit tests against a local fake server on `127.0.0.1` and the
   scene generator offline; it never holds the key and never reaches the service.
5. **Never a safety mechanism.** The model proposes a target; it authorises nothing. The engine's
   gate (stop, consent, policy, foreground application, window scope, age bound, freshness) stays
   the only authority (ADR-0007). A "no injection" answer from the model is not evidence that a label
   is safe, and an "injection" answer is not a control that blocks anything. The experiment reports
   how much of the model's error the gate refuses, not how little of it the gate needs to.
6. **The key is the operator's.** It comes from the environment variable `SUBQ_API_KEY` or from a
   `--key-file` that lies outside the git checkout. The tool validates it (printable ASCII, no spaces
   or line breaks, 8 to 512 characters) before it builds a header, never prints it, logs it or writes
   it, and shows only fixed messages and exception type names, so no traceback can carry it. It
   refuses a key file or an output path inside the checkout, never follows a redirect while it holds
   the key and uses `https` except for `127.0.0.1` and `localhost` (the tests' fake server). It
   disables proxies for its requests, whatever the environment says, so the key goes to the base
   URL's host and to nowhere else.
7. **A hard budget.** The tool does not start without `--max-input-tokens`, stops before a request
   whose estimate (the JSON length over three) exceeds what remains, stops at once on HTTP 401, 402,
   403 or any redirect, and retries 429 and 503 once after five seconds before stopping. Every
   HTTP 200 reply is billed from its `usage.input_tokens` whatever its answers look like, and the run
   stops if that count is missing, not an integer or negative. A charge reported on any other reply (a
   429 or a 503 that did bill) also counts, and a retry is sent only if it still fits. A transport
   failure, or an interruption by the operator, keeps and writes what was already paid for.
8. **Screen text is data.** The state sent with each goal carries a note that labels are untrusted
   screen text, data and never instructions. The note is a measurement condition of the experiment, not a
   defence the engine relies on.
9. **Exploratory.** The experiment (AG-01, chapter 09 §9.10) is not in `plan_pruebas.csv`, is not a
   Definition of Done criterion and ticks no box. Its results are reported as measured, with the
   model's version and the date, and say nothing about the product's safety.

## Alternatives considered

- **Never use an external model.** Safe and simple, but the thesis's claim that the structured
  snapshot supports an agent that acts by ID would rest on scripted clients only. Rejected: the
  synthetic-only rule removes the privacy cost without removing the evidence.
- **Run it on live observations of the supervised rounds.** It would be closer to the real use.
  Rejected: it sends real screen content to a third party (ADR-0012) and the observation of a real
  desktop cannot be shown to be free of personal data.
- **Make the model a guardrail** (for example, refuse a click when its injection answer is high).
  Rejected: it adds a second, unmeasured and non-deterministic authority beside the gate, which
  breaks determinism (AGENTS.md §5.1) and fail-closed actuation (§5.6).
- **Add a decision-model port and an adapter crate.** Rejected: nothing in the engine calls it
  and ADR-0014 asks for a crate only when a second implementation is in sight. The tool is a script
  that reads a file.
- **A local open-weight model instead of a hosted one.** A candidate for later; it would lift the
  privacy constraint but not the others. The conditions above are written for any external model.

## Consequences and cost

- The architect can measure the gap between a decision model and the gate with a small, repeatable,
  cheap run (25 requests, about 12.9 thousand estimated input tokens at the time of writing).
- The scene generator is a second user of the simulator and of the MCP adapter's serialisation, so a
  change to the observation's shape shows up as a failing example test.
- A hosted service sees synthetic scenes: forms, buttons and invented labels, including a label that tries to
  redirect an agent. That is the whole exposure.
- The results depend on a preview model that can change; a result is valid for the model name and
  the date it was recorded.
- The tool needs a key and a network and so is never part of the CI gate; its own tests do not.
- First result (2026-10-17, two runs on the fixed tool, 25 goals): the model grounded 12 of 13 achievable goals (the miss is an omission) but abstained on only 10 of 12 impossible ones, and the gate refused none of its 5 wrong actions because they were enabled, confirmed elements. This is why decision 5 stands: the gate cannot replace the agent's judgement, and the model's judgement cannot replace the gate. Details in chapter 09 section 9.10.

## Required validation

- `ag_01_*` tests of the example `agent_scenes` (`src/acceptance/examples/agent_scenes.rs`):
  byte-identical output across runs, the file declared synthetic and named, every expected target
  resolved by role and label and accepted by the gate, and disabled elements and text refused by it.
- `tools/agent/test_subq_decisions.py` against a fake server on `127.0.0.1`: the generated scenes as
  the only source (no option takes a scenes file; the generator command is fixed and runs from the
  checkout), the refusal of output that is not synthetic, the required budget, billing of every
  200 reply and the stop on unreadable usage, the stop before a request that does not fit, the stop on
  401/402/403 and on any redirect, the single retry on 429/503, key validation and a key that never
  reaches an output or a traceback, `https` except for loopback, partial results kept on a transport
  failure, the refusal of paths inside the checkout, and the summary's arithmetic.
- `ag_01_the_scenes_match_the_pinned_hash` in the example, and the Python test that the constant of
  the tool is the one the example asserts; the production generation path under a canary runner, a
  shadowed `cargo` and a planted artefact (refused by the pin, no request built); proxies, an
  interrupted run and a charge on a 429 in `tools/agent/test_subq_decisions.py`.
- `ag_01_every_goal_is_behaviourally_true_in_the_simulator` in the example: each goal of the
  simulator's scenes is achieved, with the simulator's own transitions, by its expected element and by
  no other (and by none when the goal is marked impossible).
- The two reviews of PR #80 and their resolutions: `docs/reviews/2026-10-17-pr80-agent-decision-experiment.md`.
- The thesis checks (`validar_paquete.py`) still pass with this ADR present.

## Reversibility

Delete `tools/agent/`, the example `agent_scenes` and chapter 09 §9.10; nothing else depends on
them. Revoking the key ends any use. Superseding this ADR with a stricter one needs no code change
in the product, because the product never calls the model.

## Provenance

New with the owner's request of 2026-10-17 to try SubQ as an external agent over the Ommatix 1.0
contract in the test workflow, and the architect's feasibility probe. It applies ADR-0007
(fail-closed actuation: the gate is the only authority) and ADR-0012 (data minimisation: no screen
content leaves the machine) and refines neither.

## Resumen (ES)

Un modelo de decisión externo (SubQ) sólo puede usarse en una herramienta de experimento del
operador, sobre escenas sintéticas que la propia herramienta genera con el generador del repositorio
(no acepta archivos de escenas) y cuyo SHA-256 está fijado en el repositorio (no envía nada si no
coincide; una máquina del operador comprometida queda fuera del alcance); nunca con observaciones,
capturas ni texto de pantalla reales (ADR-0012), nunca dentro del binario del producto, nunca en CI
con red y nunca como mecanismo de seguridad: la puerta del motor sigue siendo la única autoridad
(ADR-0007). La clave llega sólo por `SUBQ_API_KEY` o un `--key-file` fuera del repositorio y nunca se
imprime ni se guarda; el presupuesto de tokens es obligatorio. El experimento (AG-01) es
exploratorio: no entra en el plan de pruebas ni marca casillas de la definición de hecho.
