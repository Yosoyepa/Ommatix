# Step 5 of AG-03: independent review of the `SendInput` helper, the guards and the process harness

Reviewer: an independent Claude session (read-only, fakes only, an audit hook that rejected any real DLL load, symbol
lookup, subprocess or socket operation), 2026-10-20, on `f16bb60` (main after PR 101): **NOT RELEASED**, three P1, one
P2 and one P3. This file records, for each finding, the resolution and the regression test that covers it (AGENTS.md
rule 10) and the red-first evidence (rule 11). Everything here is fake-only: no real input, window, foreground, key
state, job, DLL, screen or provider was used by the review, by the fixes or by their tests.

## Process

* For each finding the regression test was written first and run against `f16bb60`; the red output was kept
  (`step5fix_red\test_step5_red_f16bb60.log` beside the task prompt, outside the repository, from this Windows
  machine, and `test_step5_red_f16bb60_linux.log` from Linux under WSL). `tools/agent/ag03/test_step5.py` has 29
  tests. At `f16bb60`, 22 fail on Windows (37 failures and 5 errors counting sub-cases), 2 POSIX-only tests are
  skipped there (on Linux 18 of the 21 tests that run fail) and the 5 that pass are controls (a clean delivery, a
  held modifier, an idle attested desktop, a clean session, a start that cannot create the child). Four of the 22 are
  pure-decoder tests of functions that did not exist; they are written with the fix and are not claimed as
  fail-first.
* The native boundary of the tests is a set of Python objects standing in for `ctypes.WinDLL` (`NativeWorld`,
  `JobWorld`); the sender, the clock, the operating system and the child process are fakes. A guarded test runner
  that refuses any real DLL load or `CREATE_SUSPENDED` child was used to run the suite on this Windows machine. The
  tests of the repository that start a real Python child under the owned-process-tree runner create a real job
  object on Windows and were therefore **not run on Windows by this work**; the whole `tools/agent` suite was run on
  Linux (WSL, Python 3.13) instead, where the same tests start a real child with a process group and no Win32 call.
  The Windows branch of the new start logic is covered only by the fakes.
* Nothing native was validated. Whether `OpenInputDesktop` behaves as documented on the secure desktop, whether a
  topology change lands the click where the geometry check claims, and how large the residual race is, are the owner's
  step-6 checks (list at the end).

## What a live run must still verify (the reviewer's list, plus what these fixes add)

These are the owner's checks of step 6; none was executed by the review or by this work.

1. Step 2 capture admission on every synthetic target style, including the foreign window present only during acquisition.
2. Effective process and thread DPI contexts, click landing across the allowed primary-monitor scales, negative virtual
   origins, **topology-change refusal** (the geometry check of S1 is untested against a real display change) and the full
   target-window placement.
3. Guard behaviour during foreground and focus changes, movement, exit, occlusion, helper windows, elevation,
   **active-desktop changes** (S4's attestation against a locked or secure desktop), held modifiers and the operator's
   stop, including changes during native evidence acquisition; report the **residual query-to-dispatch race** without
   claiming an atomic target-directed `SendInput`.
4. Input-state interference (held buttons, capture, partial insertion) and the operator procedure for an uncertain batch.
5. Native job ownership: termination on genuine harness death, interrupted startup and interrupted cleanup, descendants,
   no runnable child before assignment, conservative lock disposition. The fakes and the 0x2000 constant do not prove
   kernel enforcement.
6. Each model's gate (step 3b) and the isolated production route and proof before any recipient receives images.

The price of R104-2 is a conservative lock in the rare case that `CreateProcess` itself fails with an error other than a missing
program or directory (for example an invalid executable): the operator removes the lock by hand after checking. That is the
fail-closed side, chosen over guessing.

Not validated natively, for the owner's step 6 (additions to the list above): that `OpenInputDesktop` with the hook and journal
rights **succeeds** on a normal interactive session of the owner (a refusal there would stop every live action, which is safe
but must be known), that it fails as expected on a locked or secure desktop, and the integrity-level read.
